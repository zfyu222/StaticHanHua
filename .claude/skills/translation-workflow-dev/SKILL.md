# 翻译流程开发与优化

用于修改翻译工具和流程本身。按用户要求区分分析与开发；仅分析时不改代码。用户已要求：使用模拟 API 验证的流水线改动，还需在接口有效时进行必要的小样本真实 API 验证，按下文执行，不重复询问；这不代表启动全文翻译。用户本次明确要求只读、禁止执行或禁止请求时，以本次限制为准。

在 StaticHanHua 工作区根目录解析下文路径。先读工作区 AGENTS.md 和 `.agents/skills/game-translate/SKILL.md`；涉及某游戏时，按需读该项目 README、配置及相关日志。API 凭据不进入输出、日志或测试夹具。

## 首要原则：让 API 模型的负担最小化

模型负责理解、翻译和真实语义判断；程序负责已知信息、机械处理和执行控制。设计输入和回复时，逐字段判断：这项内容需要模型作出新判断，还是程序已经知道、可以确定性恢复？后者优先交给程序。

- 不要求模型抄写长哈希、任务 ID、版本或本地路径。使用批内短编号，通过对应 session 的映射绑定任务、快照和范围；不按回复顺序猜测对齐。编号必须校验未知值、重复和越界引用。
- 原译未变可用显式 `keep:true`，修改时只输出一次完整新译文。修改前后全文、冗余覆盖清单和纯元数据标记可由程序恢复；缺少字段不能自动解释为通过。
- 同批术语去重传入，每条保留明确的命中引用；术语例外引用短编号并提供具体理由。删除提取任务 ID 等追踪信息，保留候选差异、出处、语境和真实审校理由。
- 只提供本阶段需要的指令、数据和输出结构示例。避免让 API 模型承担文件读写、工具调用、轮询、调度、自行检查协议或重复自审。
- 精简不能删除必要原文、保护映射、锁定约束、关联候选、诊断或审校证据。四维/六维检查、来源摘录、修改理由和争议判断仍由模型真实提供；程序不代填 pass、完成声明或冲突确认。
- 对完整协议作展示和传输适配，接收后恢复为共同结果再验收。保留原始回复及完整结果，便于定位模型错误与程序错误。

不以字数最少作为唯一目标：短编号、字段含义和保留/修改两条路径要清楚，避免因省略说明增加误解与重试。

## 程序设计取舍

优先选择简单、收益明确的改动。先定位实际耗时，再考虑消除重复准备、重复匹配、重复 Token 计算及重复文件/数据库读取；能在一次阶段调用中复用内存就复用。只有数据证明仍有收益时，再考虑增加线程或其他并发机制。

翻译阶段仅提供 SubAgent 与 API 两条路线，不再提供 AINiee GUI 翻译路线；AINiee 目录仅保留现有底层模块和提取工具依赖。API 与 Codex 子代理共用任务准备、拆批、持久结果和验收规则；适配 API 的输入输出不另建一套翻译流程。借鉴 AINiee 时核对实际源码和语义，验证对现有流程的适用性。

普通多轮处理尽量由一次程序调用完成，复用 Workflow、术语对象及 API 客户端。保留用户需要独立执行、检查或提交版本库的阶段边界，不为复用缓存擅自串联翻译与审校；达到既有停止条件或需要实际语义裁决时返回主流程。

格式、字段类型和引用范围错误，在当前任务内按既有次数上限及时重试；整轮语义验收及失败项修复继续遵守共同规则。不能因失败不断重建任务、重置尝试预算或重派已通过项。

接续优先保证已完成的翻译/API 任务不用重做；准备阶段允许重新计算。优先复用已保存的完整回复、任务状态和 session 映射，不为保存准备进度引入复杂系统。用户明确不需要兼容旧任务时，不额外设计迁移层。

## 性能数据与验证

改动性能路径时保留可比较的阶段计时，尤其是准备耗时、首次请求前耗时、API 等待、收集/校验及重试；按有意义的进度间隔输出完成量。结束汇总总墙钟时间、请求/失败/重试数量和服务端报告的输入、输出、总 Token。缺少 usage 标为未知，不能填零或把本地估算当账单；并发累计耗时和嵌套计时不能相加冒充总用时。

以相关小样本和有意义的回归验证为主。协议改动应覆盖正常回复、保留/修改路径、引用越界、缺少真实证据、失败重试和已落盘回复的恢复；共用协议改动还要检查另一执行方式。仅改变文档或低影响可逆配置时，不添加只比对实现文字的测试。

凡使用模拟 API 验证的流水线改动，模拟测试通过后，若已配置的接口有效，必须再做小样本真实 API 测试，不能以模拟通过作为全部验证完成的依据。沿用用户所选接口及模型，不擅自切换服务；事先限定样本范围与请求上限，覆盖相关分支后停止。接口不可用或缺少配置时，明确说明真实验证未完成及原因，不反复请求或将失败当作已验证。

真实测试走正式输入生成、API 请求、解析、落盘及共同验收链路，按改动范围覆盖首轮、返修或审校的相关步骤；不能只验证接口连通或拿到一段 JSON。选择能触发改动分支的代表性样本，例如保护标记与已还原原始标签/变量、保留已有译文、修改译文及必要的多轮接续。保留模型实际回复，不先人工修成模拟测试预期的规整格式再声称通过；避免模拟模型始终输出理想协议而掩盖输入与验收不一致。

真实 API 测试能暴露模拟未覆盖的模型行为，但不保证一次小样本发现所有问题。将实际暴露的失败回复整理为去除凭据、可重复运行的回归夹具，覆盖正确的等价表示以及真正缺失、重复或损坏内容仍被拒绝的情况，再验证修复。

真实性能基准优先对生产数据作只读快照，在临时夹具中测试。真实 API 测试按用户已授权范围小样本执行；报告清楚区分模拟测试、本地 Token 统计与服务端实际 usage。开发过程中不顺带改写正在翻译的项目状态。

交付时说明改动影响哪些步骤、模型少做了什么、程序如何恢复和验收、验证结果及仍未完成的事项。同步修改受影响的流程说明，保持原则与程序实际行为一致。
