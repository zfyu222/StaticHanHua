# 翻译阶段双工作流设计

设计日期：2026-10-12。实现更新：2026-10-13。命令行程序及技能路由已实现，Luna 并行合成样本全流程通过；API 模拟验证通过，真实 API 尚未验证。具体支持范围见同目录 README.md。

## 已确定的边界

- 总体仍是初始化及提取、翻译、回填、发布；本文所有子阶段均属于翻译阶段内部。
- 保留现有 AINiee 工作流、程序及改进；首次进入翻译阶段且未指定方式时，由用户选择 AINiee 或自定义工作流。已选方式持久化，恢复时不重复询问。
- 自定义工作流再选择 Codex 子代理或 API 程序执行。不能因失败、额度不足而未经选择切换到付费 API。
- 当前用户已指定可用 Luna 子代理；子代理并发按实际会话容量调度，不硬编码成所有环境固定三个。
- 源文与正式译文继续位于项目根目录。翻译阶段中间产物统一放在 `Projects/{GameName}/TranslateFiles/`，绝不写入指向游戏本体的 `Game/` 链接。
- 基础文档只说明工作流选择、输入输出、TranslateFiles 位置。子阶段、调度规则、修复命令和质量门槛由 game-translate 技能及引用文档维护，项目 README 只记录实际方案、结果和待确认问题。
- 新项目按新目录规则执行；既有项目不在设计阶段批量搬迁。后续提供显式迁移工具，核对所有路径引用后再迁移。

## 结构与复用策略

工具放在 `Tools/localization/`。公共层负责项目配置、任务状态、批次、质量检查、审计和导出；执行后端只负责把同一任务变成模型输出。

```text
game-translate 技能 / Codex 主代理
  ├─ AINiee 入口：沿用现有 GUI 工作流
  └─ 自定义入口：本地流程程序
       ├─ 共享任务、配置、术语、检查与结果提交协议
       ├─ Codex 后端：生成任务文件 → 主代理调度子代理 → 提交结果
       └─ API 后端：程序执行请求 → 提交同格式结果
```

普通 Python 程序不能调用当前聊天内部的 spawn_agent。Codex 后端由技能指示主代理调用平台的子代理工具；程序提供 prepare、claim、submit、status 等文件任务操作。API 后端由程序运行，沿用同一验收路径。阶段可选择不同后端，例如 API 初译、Codex 审校，前提是选择及预算已明确。

## 翻译内部流程

1. **准备**：读取项目档案及源文；使用 CSV 逻辑记录计数，保存源文快照、hash、稳定 ID 与提取上下文。生成项目独立配置：语言、文体、角色口吻、禁翻/保护规则、术语匹配选项、批次预算、后端、模型、重试及审校策略。
2. **术语提取**：这是正文翻译前的首项语义工作。分批收集候选并保留出处，汇总去重及变体候选。覆盖全源文，不能仅以少量开头文本代表全文；候选汇总、整理及审校完成后才进入正文翻译。
3. **术语审校**：执行原有冻结 → 程序检查 → 带原文依据的语义审校 → 保存决定、修改/隔离表 → 校验的固定步骤。AI 可自动完成有依据的决策；不能把自动检查通过标记为语义审校完成。无法判断的项保存待确认或暂不作为强制术语，完成明确处理并冻结正式表后才放行正文任务。正文翻译不承担持续提取或扩充术语的职责。
4. **试译**：按文本类型选代表样本，核对译文、保护规则和文体，调整配置后冻结本轮规则。不强制向用户逐批确认。
5. **批次翻译**：优先按剧情/对话/资源分组，在 token 预算内切分；无提取映射时只提供相邻记录并注明上下文不确定。同一原文处于不同语境时不自动共用译文。程序按本批原文及附带上下文，从已冻结的完整术语表筛选匹配项，连同相关变体、角色信息及语境例外形成任务术语子集；翻译、审校、润色子代理无需浏览完整术语表。匹配沿用统一规则，任务注明全局术语版本和匹配规则版本，并保存术语到记录的关联。
6. **程序验收**：缺失/重复/越界 ID、源文变化、错误版本、占位符与标签损坏均拒绝提交。标点、长度、疑似残留原文等按规则生成问题；合理保留原文不得一律视为失败。
7. **语义审校**：全量逐条覆盖，审校任务同时读取原文、译文、上下文与术语。校验器无法判断的误译、漏译、逻辑和人物口吻由 AI 检查，疑难项升级给主代理。独立任务审校不能宣称完全消除同模型偏差。
8. **按需润色**：可按 UI/剧情等类型启用；有原文、有术语约束，仅提交必要改动，改后重新校验与检查原意。
9. **全局终检与导出**：核对覆盖率、术语及人物口吻一致性、未解决问题和源文 hash，原子导出项目根目录正式译文。必需检查失败时不能标记翻译完成。输出仍为无表头、单列、与原文 CSV 逻辑记录一一对应。
10. **交接**：README 记录实际工作流、执行后端/模型、术语版本、覆盖及验收结果，提交适合入库的文件；随后沿用现有回填与发布。

## AI 介入与版本控制

- 主代理可在批次完成、质量异常及阶段切换时介入，检查报告、修正规则、追加审校任务。API 模式同样输出结构化状态与报告，供主代理检查。术语整理是正文前置阶段，不在正文任务中设置新术语收集循环。
- 若验收发现术语准备遗漏或程序筛选错误，记录为前置阶段/工具缺陷，由主代理安排修复、重新冻结及增量复查；子代理不得自行新增术语。这是异常修复路径，不作为正文阶段的常规工作。
- 程序必须支持暂停领取新任务、等待正在执行的任务提交、再变更规则；正在运行的请求不保证可取消。
- 每个任务冻结源文、配置、术语、提示词及协议版本，附 hash。调整后创建新修订，旧版本在途结果只能存为历史，不能进入新版本正式结果。
- 术语/规则变化通过命中关系定位受影响记录，标记待复查；其他记录不重复翻译。提示词变化无法证明影响范围时采用保守失效策略。
- 人工或主代理确认的译文支持锁定，重试与润色不能覆盖；解锁需记录理由。
- 自动修复、审校和润色分别设最大轮数。用量/费用设预算，额度不足或持续失败暂停并保存问题，不形成无限重试循环。
- 自动执行覆盖能判断的步骤；存在关键未确认项时准确报告，不伪造已审校状态。

## 数据、任务与目录

```text
Projects/{GameName}/
  README.md
  {gamename}_text.csv
  {gamename}_text_translated.csv
  TranslateFiles/
    TranslateDoc.md
    config/                # 脱敏项目配置、风格与角色规则
    source/                # 源文索引、hash、上下文及快照
    glossary/              # 原表、检查、审校决定、审校版、manifest
    tasks/                 # 各子阶段任务包与领取信息
    results/               # 按任务及尝试分别保存结果
    reports/               # 占位符、术语、语义、终检报告及问题清单
    state/                 # 队列状态、修订号、锁、断点
    history/               # 规则和译文变更记录
    logs/                  # 脱敏运行日志
    cache/                 # 可再生缓存和 AINiee 项目缓存
    backups/               # 完整缓存及修改前备份
```

AINiee 模式的翻译准备/审校文件也遵守 TranslateFiles 规则；正式翻译继续在原 GUI 内执行，不改写现有全局配置。新 AINiee GUI 项目导入 TranslateFiles/source 下的快照，沿用“缓存随输入目录”改进，将缓存留在该目录内；无需修改 AINiee 本体。搬移已存在缓存前先关闭程序、备份并验证。具体文件名可调整，目录边界固定。

队列至少保存 task_id、stage、record_ids、revision、input_hash、backend、status、attempt、worker、lease 与错误原因。领取原子化、任务带租约；超时恢复需核查 worker 状态。每次尝试输出独立文件，提交按任务/修订幂等处理，过期领取不得覆盖已验收结果。

结果按 record_id 对齐，不依赖 AI 输出顺序；检查额外 ID、缺项和冲突。只由程序提交正式状态和合并译文，子代理不能直接修改源文、冻结术语或最终 CSV。

状态存储选择在小型原型中验证：优先标准库 SQLite 事务管理并发与修订，JSON/JSONL 作为可读任务、结果和报告；不新造不具备事务的共享 JSON 队列。

小型配置、规则、术语审校及交付报告按项目规范入库。密钥、完整缓存、备份、原始请求调试、庞大运行日志与队列运行状态默认忽略。API 凭据通过环境变量或独立本地凭据引用提供，禁止写入任务包和 Git。

## 开发顺序与验收

1. 完成复用可行性验证和改进回归样例，固定 AINiee 基线；验证无 GUI 加载、不污染 Resource/config.json、不影响原工作流。
2. 开发公共 CLI 与任务协议：准备、配置、分批、领取、提交、状态、暂停/恢复、检查及导出；先用模拟执行验证记录完整性、并发、过期结果、版本变更与中断恢复。
3. 接入 Luna 子代理任务模式及技能调度规则，用完整小章节验证术语到交付全过程。
4. 接入 AINiee API 适配器，通过无网络 mock 检查重试、限流、取消、预算、错误脱敏；配置用户选择的接口后再进行小规模真实请求验证。
5. 整合术语、语义审校、润色、增量复查和 API 运行中的 AI 检查点；两后端必须通过同一套提交质量门槛。
6. 更新 game-translate 入口及内部 references，适配两种工作流的 TranslateFiles 路径；基础 AGENTS/README 只改入口选择和目录说明，不铺开子阶段细节。

完成标准：保留 AINiee 原工作流；两个自定义后端可选择、可恢复；本地修复有行为验证；任一后端产出能通过相同质量门槛；失败/未审校/过期结果不能导出为已完成译文；所有中间产物遵守 TranslateFiles 边界。
